0. 主线一句话#

智能体 = 模型 + Harness + 工具 + Skill：模型负责“想”，Harness 负责“跑得稳”，工具负责“够得着外部世界”，Skill 负责“把一类任务的做法固化下来”。Task1 的两讲分别在讲这条链的前半段（03：Agent 怎么组成、怎么循环）和后半段（04：Skill 怎么写、怎么被调用）。

两讲的落点也不一样：

  • 03 讲回答“为什么会失败”——同一个模型，Harness 做得糙就翻车，做得细就像样（03-P6~P11 的递进图）。
  • 04 讲回答“怎么让成功可复现”——把一次成功的做法写成 Skill，下次不用重新摸索。

1. 三层定义：LLM / Harness / Agent（03-P3、P12、P15）#

概念 课件原定义（03-P3） 我的理解
LLM 经海量语料预训练、具备语言理解与生成能力的神经网络模型 只有“一次性输入→输出”的能力，本身不记事、不执行
Harness（驾驭层） 承担运行调度、能力扩展、安全约束和效果保障的工程化支持框架 把模型包成一个能持续干活、能被约束、能留下痕迹的系统
Agent（智能体） 感知环境并作用于环境的实体 模型 + Harness 的合体；“感知”靠上下文，“作用”靠工具

03-P12 给了一个非学术但好用的式子：

Agent = Model + Harness

Harness 具体干什么，03-P15 列了六件事，这六件事就是后面所有“为什么会失败／怎么修”的抓手：

  1. 整理上下文
  2. 调用模型
  3. 调用工具
  4. 保存运行记录
  5. 检查权限
  6. 控制运行流程

03-P15 的结构图值得记住：用户指令进 Harness → Harness 把“任务、上下文”喂给 Model → Model 回“回答、工具请求” → Harness 去调 Tool（检索文献／读写文件／运行代码）→ 结果再回上下文。注意 Model 从不直接碰工具，中间永远隔着 Harness。

2. 学校类比：为什么 Harness 是“体系”而不是“胶水”（03-P13、P14）#

学校（Multi-Agent System） 智能体系统
成员：教师、学生、教研人员 Agents
工具与资源：教材与题库、学习平台与器材 Tools
学习活动：上课、练习、测验 Workflow / 任务执行
教学管理：人员分工、课程安排、考核评价 Harness

这个类比的价值在于把 Harness 从“接口层”提升成“制度层”：光有聪明的学生（模型）和教材（工具）不构成学校，还缺排课、考核、监督、记录。 03-P11 的最终形态正好演示了这一点——家长下指令“考到 100 分”，最终结果是 70 分；中间多出来的东西是：教学组备课、skill（教辅）、《如何上课不走神》《如何按时做作业》《如何考前抱佛脚》三份 skill、教师监督、以及“核验结果”这条独立回路。

这里有个容易忽略的设计点：核验回路是独立的。 干活的是学生，核验的是教师，两者分开——对应到智能体，就是“生成的 Agent”和“检查的 Agent”不能是同一个上下文。

3. LLM 的两个特性，就是 Harness 存在的理由（03-P5）#

特性 课件表述 后果
上下文限制 一次能读进去的文字有限（上下文窗口）；每次调用都是一次性的，前面的话要重新拼进输入；超出窗口会被截断 长任务必须做上下文整理、压缩、外置记录，否则早期信息静默丢失
幻觉 知识止于训练数据；没见过的东西照样答得流畅 真假不能靠“读起来像”，必须靠工具核实（课件举例：论文可能并不存在）

一句话串起来：上下文限制 → 必须“整理上下文 + 保存运行记录”；幻觉 → 必须“调用工具 + 核验”。 这两条正好对应第 1 节 Harness 六件事里的一半。所以 Harness 不是工程炫技，是被 LLM 的两个缺陷逼出来的。

4. 一次文献检索，内部到底发生了什么（03-P16、P18、P19）#

03-P16 把一次工具调用拆成六步对话，这是全课最该背下来的时序：

Model        → 生成检索请求：主题、关键词          （基于：任务 + 工具说明 + 已有记录）
Harness      → 检查参数和权限，调用检索工具
Tool         → 返回检索结果或错误信息
Harness      → 将检索结果加入上下文
Model        → 生成回答，或继续提出检索请求

三个细节：

  • “输入任务、工具说明和已有记录”——模型每次都要重新拿到工具说明（它不记忆工具列表），所以工具描述写得好不好直接决定调用质量。
  • “检查参数和权限”发生在 Harness，不是模型自检。权限是外部约束，不能交给被约束者。
  • “错误信息”也是正常返回值，会进上下文。所以工具的错误提示写得清楚，模型才有机会改；反过来，工具静默失败会让 Agent 编一个结果出来。

03-P18 把同一个时序放大成多 Agent 版：用户 → 主笔人 Agent（查资料、读文献、写论文）＋ 监督者 Agent（监督、核验结果）＋ skill 专员 Agent（去找合适的 skill）→ 输出“完善的文献综述”。注意“找 skill”本身也被拆成了一个 Agent 角色——因为 skill 多了以后，“选对 skill”就是一项独立能力。

5. Harness 的运行循环（03-P23）#

课件给的 8 步，本质是一个带兜底的 while：

1  准备：任务、工具说明、已有记录
2  在权限、次数和时间限制内循环：
3      调用模型，获取回答或工具请求
4      如有工具请求：执行调用，更新上下文，继续循环
5      如满足完成条件：输出结果，结束
6      如需人工处理：暂停，并说明原因
7      其他情况：补充信息，继续执行
8  达到运行限制时：停止并报告当前进度

值得单独抄下来的三行是 2、6、8：

  • “在限制内循环”——没有次数/时间上限的 Agent 会陷入死循环，烧钱且不收敛。上限是设计的一部分，不是可选项。
  • “暂停，并说明原因”——人工介入要有交接说明，否则人接手时要重新读一遍全部上下文。
  • “停止并报告当前进度”——超限退出不等于失败退出，关键是要留下“做到哪了”。这条和第 1 节的“保存运行记录”是一套的。

6. ReAct：循环里的最小认知单元（03-P24、P25）#

Thought（LLM 推理） → Action（工具调用） → Observation（反馈） → 再 Thought …… → Answer

03-P25 的具体例子（文献检索）：

  1. 分析问题 → 调用网页搜索 → 得到搜索结果
  2. 下一步决策 → 调用 WOS / API → 得到文献结果
  3. 综合判断 → 输出最终回答

要记住的是“Observation 回到 Thought”这条虚线，它不是单向流水线。Agent 与 Workflow 的差别，全部体现在这条回边上：下一步做什么，是看上一轮结果现决定的。

7. Workflow 与 Agent 循环的分工（03-P26）#

工作流（Workflow） Agent 运行循环
决策方式 预先规定步骤与分支 运行中选择下一步操作
课件例子 网页检索 → 是否成功？失败走数据库接口 → 保存结果 模型选操作 → Harness 执行 → 工具返回 → 再选
优点 可控、可测、可复现 灵活，能处理没预料到的情况
代价 预料之外的失败没法绕 不可预测，可能绕远或发散

实践结论（我的判断）： 科研任务里两者是嵌套关系——外层用 Workflow 固定“必须经过哪几步”（如：检索→筛选→阅读→写作→核验），内层每一步用 Agent 循环处理“这一步具体怎么做到”。03-P19 的表格也是这么分工的：Workflow 规定顺序，Skill 提供方法。

8. 失败与变通：能力要留多条路（03-P20~P22）#

课件用一个很具体的问题推进：“查资料这一步是怎么实现的？调用网络搜索 tool 失败了怎么处理？” 答案是：变通调用 API（03-P22）。

这条讲的是鲁棒性设计，落到我自己写 Agent 时是三条：

  1. 关键能力至少两条路径（搜索工具 ↔ API / 数据库接口）。
  2. 失败必须显式暴露给模型，让它有机会换路，而不是抛异常终止。
  3. Harness 里要能“降级”——先试 A，A 不可用改 B，都不行才报人工。

9. 六个概念的分工表（03-P19，最值得背的一页）#

概念 主要作用 文献综述中的例子
模型 Model 理解信息、推理和生成内容 判断文献相关性，选择下一步行动
工具 Tool 执行检索、读取或保存等操作 检索数据库、读取 PDF、保存文件
技能 Skill 提供操作方法、脚本和资源 检索方法、筛选规则、引用核验要求
工作流 Workflow 规定任务的步骤和执行顺序 检索、筛选、阅读、写作、核验
运行框架 Harness 管理模型调用与任务执行 整理上下文、调用工具、保存运行记录
智能体 Agent 根据任务采取行动 多次检索文献，完成资料查找

辨析要点： Skill ≠ Tool（Tool 是“能做什么”，Skill 是“该怎么做”）；Skill ≠ Workflow（Workflow 管顺序，Skill 管每一步的做法）；Harness ≠ Agent（Harness 是设备，Agent 是那个“实体”）。

10. MCP 与 Skill：接得上 vs 做得稳（04-P12）#

04-P12 的一句话对照，把两者的分工讲透了：

MCP（模型上下文协议） Skill（技能）
定位 服务连接器 流程沉淀器
解决 让智能体接得上外部工具或数据库 让智能体做得稳
内容 规范化的接口（工具/数据源） 完成任务的步骤、规则和资料，沉淀为可重复调用的工作流
例子 “明天下午去北京开会要带伞吗？”→ 气象局接口查天气 → 回答 检索方法、筛选规则、引用核验要求

同一页的“能力积木”图里，Harness 下面并列十块：联网搜索、网页操作、文件处理、代码执行、MCP、记忆、Skill、知识库、多模态、电脑操作。这说明 Skill 不是外挂，而是和工具、记忆、知识库同级的“能力来源”之一。

11. Skill 的目录结构（04-P13）#

skills/<skill-name>/
├── SKILL.md          # 元数据 + 工作流程；唯一且必需的入口
├── scripts/          # 辅助脚本
├── references/       # 参考资料
└── assets/           # 模板、图片等素材
  • 最小可用 Skill 只需要一个 SKILL.md，其余目录随任务需求增加。
  • 后三个目录是“按需加载”的，这点在第 13 节的调用机制里会变得关键。

12. SKILL.md 的三个部分（04-P14）#

04-P14 用真实文件 research-question-decomposer/SKILL.md 逐段解剖，三段结构：

12.1 元数据（frontmatter）#

---
name: research-question-decomposer
description: 保留用户的原始科研问题，转述并对其真实研究需求，再推荐可用于后续文献检索的子问题；用于文献调研开始前的问题澄清；不生成文献综述。
---

这是全篇最该反复推敲的一行。 因为调用时模型只看得到 name + description（04-P15），description 就是检索键：

  • 写清“做什么”（保留原始问题、转述、推荐子问题）
  • 写清“什么时候用”（文献调研开始前的问题澄清）
  • 写清“不做什么”（不生成文献综述）——防止被误触发

12.2 工作流程#

课件里的三段式，逻辑很清楚：

  1. 保留原始问题：用户输入原样记录为 Q0，不用改写版替代。—— 保真，后面每一步都能回溯到用户原话。
  2. 转述并对齐需求：用简洁语言说明对需求的理解，重点识别“研究对象 / 想了解或判断什么 / 已给出的时间、场景或范围”；不擅自增加研究方向，不影响整体拆解的小歧义标 [待确认]；只有不同答案会导向完全不同的研究方向的，才向用户提问。
  3. 推荐可检索子问题：通常 3~5 个，每一条要“能单独用于后续检索、只关注一个方面、彼此尽量不重复、合起来能回答原始问题”，并附一条简短理由。

三个设计手法可以直接搬到自己的 Skill 里：

  • 编号锚点（Q0、A1）：让后续输出可引用，也让用户能指着说“这条不对”。
  • [待确认] 分级：不是所有歧义都值得打断用户，只有“方向级”歧义才问。
  • 量化的产出标准（3~5 个、四条件）：把“好”写成可检查的约束，而不是“请给出高质量的子问题”。

12.3 输出格式#

给了一段 markdown 模板：## 1. 原始问题 Q0 / ## 2. 需求对齐 转述 + 待确认 / ## 3. 推荐的可检索子问题（子问题 | 推荐理由 表格）。

04-P14 右侧的实际输出截图值得对照看，它比模板更细：

  • 开头先声明“用时 30s 左右”和“在你确认前，我先不生成检索式或直接搜文献，避免最后得到一份泛泛的热点清单”——把工作边界和下一步前置声明。
  • 需求对齐里直接列出三个具体待确认点：“近五年”按滚动时间还是 2021–2025 五个完整年度？是整个高分子领域还是某个特定分支？用途是课程介绍、研究选题还是综述写作？
  • 子问题表 5 行（SQ1~SQ5），每条理由都指向一个判断用途：发文量与关注度（发现热点）、权威综述与路线图（专家判断交叉验证）、解决什么科学问题/材料体系/技术路线（研究内容）、代表性进展与关键突破（实质进展）、处于萌芽/快速增长/相对成熟（区分阶段）。
  • 收尾一句“下一步可以据此构建文献检索式，优先从 SQ1 和 SQ2 建立候选热点清单”——给出下一步，而不是停在交付物上。

13. Skill 怎么被调用：先匹配，再加载，再执行（04-P15）#

三列时序：用户 → Harness（智能体运行时）→ LLM。

用户：梳理低介电聚合物近期进展
        ↓
Harness 发给模型：
  User: 梳理低介电聚合物近期进展
  Available Skills（只读 name + description）:
    research-question-decomposer · query-builder · …
        ↓
模型返回：research-question-decomposer      ← 匹配（只凭 description）
        ↓
Harness 命中后再加载：
  instruction: SKILL.md
  resources: scripts/ · references/ · assets/（按需）
        ↓
完整回答：检索计划 · 证据表 · 研究简报

课件把机制概括成八个字：自动发现、渐进式披露（progressive disclosure）。

对写 Skill 的三条直接推论：

  1. description 是唯一入口。 写得含糊 = 永远不会被命中；写得过宽 = 被无关任务误命中。
  2. SKILL.md 要短。 它每次命中都进上下文；把大段参考资料塞进 references/，让模型按需读。
  3. 首屏信息要够用。 命中后模型只加载 SKILL.md，如果关键约束（输出格式、必须核验的字段）写在 references 深处，很可能不会被读到。

14. 智能体的知识从哪来，可信度差多少（04-P28、P30、P31）#

04-P28 的对照表是“为什么必须接工具”的量化答案：

模型本身知识 联网搜索 MCP（外部服务/数据库）
来源 训练过程中学到的知识 搜索引擎、出版社页面、机构网站等实时网页 OpenAlex、Crossref、学术知识图谱或内部数据库
时效性 有知识截止时间，可能过时 较强，能发现近期论文 取决于所连接数据库的更新频率
检索规模 不是真正的数据库检索，无法保证覆盖率 灵活但批量处理能力有限 适合批量查询与自动化处理
精确性 可能记错题名、作者、年份或 DOI 能直接打开来源核验，但片段可能不完整 字段更规范，但数据库也可能缺失或冲突
全文 拿不到训练语料原始全文 可能找到开放全文或出版社页面 取决于服务是否提供全文能力

04-P30 在“提出研究问题 → 收集信息 → 总结信息 → 沉淀知识”的循环旁只留了两个问题：

来源是否真实？从哪里接受的信息？

这两个问题是这一讲的价值观：AI 干活，人来判断（04-P5）。也和第 3 节的“幻觉必须靠工具核实”是同一件事的两面。

两个具体 MCP 的定位（04-P31）：

  • OpenAlex：开放学术知识图谱，检索论文/作者/机构/期刊/主题及引用关系 → 适合文献发现、引用分析、趋势分析。
  • Crossref：以 DOI 为核心的元数据服务 → 适合核验 DOI 与文献身份、补全规范题录。

我的用法约定： Crossref 当“身份证核验”，OpenAlex 当“地图找路”，两者都不等于读过全文。

15. 落到 Deep Research 流程（04-P4、P5、P33）#

04-P5 借波普尔《客观知识》把文献研究写成循环：问题 — 尝试性解释 — 批判检验 — 新问题，展开为四步：

提出研究问题 → 收集信息 → 总结信息 → 沉淀知识

04-P4 的痛点是真实的：数据库检索（WoS/Google Scholar）、文献管理（EndNote/Zotero）、阅读（浏览器/PDF）、整理（Word/Notion/飞书）之间频繁切换；直接问 AI 得到的回答“信息？思考？知识？”三问皆虚，表现为幻觉、冗长、没深度。课件给的解法不是“换个更强的模型”，而是把流程拆成可沉淀的环节，每个环节写一个 Skill。

04-P33 的小练习正是这个思路：Deep Research 三段流程图（明确需求 / 收集信息 / 完成报告），要求给「报告生成」这一段写 Skill。三段各自的内部结构也给了：

环节 内部步骤
① 需求确认 对话确认 → 问题发散 → 确认问题意图（否则回到发散）→ 收集完成
② 信息收集 当前需求 + 已有信息 → 判断信息缺口 → 新问题（拓宽）/ 继续深挖 → 查询 → 保存回已有信息
③ 报告生成 已有信息 → 制定计划（可转人工审核）→ 按章节写报告 → 完成

注意 ③ 里那个“人类审核”分支：报告生成环节不是全自动的，计划阶段留了人工确认点。这和 03-P23 第 6 步“暂停并说明原因”是同一个设计习惯。

16. 动手路径：从创造模式到复现 AI Scientist（03-P28~P32）#

03-P28 给了 DeepSeek Harness 的 4 种预设模式：

模式 能力与适用场景
标准模式 完整工具组合，适合日常编程与任务执行
PTC 模式 用一段代码组合多步工具调用，适合批量操作与多步编排
极简模式 仅 Shell 与文件编辑工具，适合最小环境下的模型评测
创造模式 检查运行时，试验和组合插件，用于创建自定义智能体预设

创造模式四步：

# 1 启动并配置
npx @deepseek-ai/dsh web
#   在「设置 / 模型」填 API Key，选择工作区
# 2 新建会话，选「创造模式」，说明任务、工具、流程与交付物
# 3 检查运行时、试验插件，保存为新的智能体预设
# 4 在新会话中选择新预设，用小任务核对结果与执行轨迹

提示词示例（可直接改用）：

请创建一个“文献综述智能体”：检索文献、提取证据、撰写综述并核验引用。复用已有工具与技能，试验缺失插件，保存为新预设，并用一个主题验证。

03-P29~P32 是以 Nature 论文《Towards end-to-end automation of AI research》（LU C, et al. Nature 2026, 651: 914–919）为目标的复现演示，搭建完成的科研预设包含：

  • 复制标准模式，配置 ecs-* 科研技能
  • 组织科研流程：提出假设 → 运行代码与实验 → 绘图 → 撰写短论文 → 评审修订
  • 保留证据链：记录真实指标和图表数据
  • 以证据账本、检查点追踪过程

“证据账本 + 检查点”是我认为整讲最实用的一条工程约束：不要相信 Agent 的自我总结，要相信它留下的原始记录。 这直接对应 Task2 要做的实验记录整理。

17. 我提炼的六条（用自己的话）#

  1. Harness 才是工程重心。 模型是买来的，“整理上下文、调工具、存记录、查权限、控流程”是自己写的，而失败几乎都发生在这五件事上。
  2. Skill 是给模型的 SOP + 可执行附件，不是文档。判据是：换个人（或换个模型）照着它能做出同样质量的结果。
  3. description 是 Skill 的检索键，写 Skill 的一半工作量在这一行上；要写“何时用 + 不用于什么”。
  4. 输出格式是约束，不是美化。 给了 schema（表格、编号、必填字段）才能被机器检查和被下游消费。
  5. 核验必须独立。 生成与检查分成不同角色/不同上下文；同时要求“来源可指认”（DOI、页码、URL）。
  6. 留痕优先于聪明。 运行记录、证据账本、检查点，比一次惊艳的输出更值钱——因为它让下一轮能接着做。

18. 自测（先答，再对要点）#

# 问题 要点
1 Harness 的六项职责是什么？ 整理上下文、调用模型、调用工具、保存运行记录、检查权限、控制运行流程
2 为什么模型不能直接调工具？ 权限与参数检查须是外部约束；调用时序、错误处理、记录都在 Harness
3 LLM 的两个特性如何逼出 Harness？ 上下文限制→整理/记录；幻觉→工具核实
4 ReAct 的四个环节？ Thought → Action → Observation →（回到 Thought）→ Answer
5 Workflow 与 Agent 循环的本质差别？ 步骤是预先规定还是运行时选择
6 Skill 的最小可用形态？ 一个 SKILL.md（元数据 + 工作流程）
7 调用 Skill 时模型先看到什么？ 只看到 name + description；命中后才加载 SKILL.md 与按需资源
8 MCP 与 Skill 各解决什么？ 接得上（连接外部服务）／做得稳（沉淀流程）
9 为什么要有“次数和时间限制”？ 防死循环与失控成本；超限要报告进度而非静默失败
10 模型知识、联网搜索、MCP 三者在“精确性”上的差别？ 可能记错元数据／可打开来源但片段不全／字段规范但库本身可能冲突
